# bimforge roadmap

What is decided, built and next for bimforge. The estimating platform's
roadmap (`docs/ROADMAP.md` in `estimating-tools`, Phase 4) lists the bimforge
rows by ID; this file holds the detail for work developed here. Update it in
the same PR that finishes or adds an item.

## Destination

BIMForge is a factory for IFC models of heavy civil work. The factory is
written once: a spec format, families, an agency's tables and dictionary, and
gates. A job is then specified, not programmed: a whole public job, every bid
item, is built from parameter files with no job-specific code, the same spec
builds the same bytes, and a model is accepted by its checks with nobody
reading it.

**The measure is yield.** For a whole-job model: how many of its bid items,
and of its elements, were built by a family, by a modified standard, by an
element placed on an alignment, or by custom code. The route each element
records (M.8) makes it countable (W.16).

|---|---|
| Reference job | A Caltrans sound wall job modelled whole by hand: 59 bid items, 1,269 elements, validated IFC4X3 |
| Built by the factory today | 0 of 59 bid items: all of it by 18 job scripts (about 4,650 lines) |
| Target | The reference job rebuilt from parameter files alone, accepted by all three checks |

## Decisions

| Date | Decision |
|---|---|
| 2026-11-11 | **IFC4X3 is the target schema, IFC4 the fallback.** IFC2X3 is not supported and is refused by name. Revit does not open IFC4X3, so Revit exchanges on IFC4. |
| 2026-11-11 | **The takeoff's input contract is an IDS document**, generated from the reader's own tables, so any IDS checker can test a Revit, Tekla or bimforge model before takeoff. |
| 2026-11-11 | **The family vocabulary lives in one dictionary file in bSDD's import format.** It is a local file. Publishing to the bSDD service, calling its API, and stamping bSDD URIs on classifications are deferred until an owner requires it or third-party models arrive already classified against bSDD. |
| 2026-11-15 | **Agency content lives in a pack: a subpackage of the wheel, `bimforge.caltrans` first.** The core keeps the kernel and the families no agency owns. A pack holds an agency's standard-plan tables, its families and its part of the dictionary, and nothing the core needs to build without it, so it can become a distribution of its own later (an extra cannot carry code or data). Only what public plans, standard plans and specifications state goes in: no prices, no bid data, no job identifiers. |
| 2026-11-17 | **The model is the estimate's record, and a quantity says how it was derived.** Takeoffs are made from the model and checked against the plan sheets, so the IFC carries, for the estimating system to keep: what each element is (its dictionary class), the dimensions that size it, each quantity's formula over those dimensions where the shape has one, where it sits, and the record of its check. All of it in standard IFC places (classification reference, quantity sets, `Formula` on the quantity, IfcApproval), so any reader gets it. BidSheet.ai's side is D8 and rows 5.16 to 5.22 of its roadmap. |
| 2026-11-20 | **Next after M.3: the road corridor family (P.6), then a command that runs the terrain (G.9), then a girder bridge family (P.5).** The girder family starts from the bespoke bridge models in the private Work repository: pick out the bridge types they build and make each one IFC4.3 compliant (typed, classified, under an IfcBridge, passing C.7, C.8 and C.12) as it moves into a family. This is ahead of P.4, which P.5 and P.6 were listed after. |
| 2026-11-22 | **A whole job is the unit, and its families come from one already built.** The corpus (M.12) models entire jobs, every bid item, from the plans and the supplemental documents; the agency's quantity sheets and bid quantities are what a model is checked against, never what it is built from, so a disagreement is a finding. The first whole-job reference is a Caltrans sound wall job modelled by hand in the private Work repository: one validated IFC4X3 site model of 1,269 elements, built by 18 job scripts. Sorting those scripts gives the family list (W rows). An agent's output is a job's parameter files, each value citing its sheet; code is a family's, not a job's. |
| 2026-11-25 | **A disputed rule is accepted with its reasoning on record.** Where a buildingSMART rule contradicts the standard it checks, bimforge writes what the standard says, and the rule goes on a short published list: the rule, the reasoning, the evidence, the report to buildingSMART and the date. A consumer accepts a model whose only rule findings are on that list, and records which. The list is reviewed at every rule-set bump and an entry leaves it when the rule or bimforge changes. It is for rules that are wrong, never for findings that are ours to fix (C.14). First entry: GRF005 (C.15). |
| 2026-11-25 | **When the goals pull apart, IFC4X3 compliance wins, then 4D, then our viewers, then other tools.** The goals: files that work in Revit, Tekla and QGIS; models that look right in our viewers; earthwork as first-class elements a 4D schedule can drive; and IFC compliance. They conflict in three places. Revit does not open IFC4X3, where earthwork, courses, roads and alignments exist; QGIS reads no IFC; and the standard way to take a cut out of the ground (the cut voiding the terrain) is what viewers draw slowest. So the IFC4X3 model is the record; 4D is served by the standard forms (E rows); our viewers are asked to draw those forms well rather than the model bent to them; and Revit, Tekla and QGIS are served by the IFC4 fallback and the georeferenced exports of the same build, carrying the same classes, dimensions and quantities. A model is authored in its map's units, so the IFC, the exports and a GIS agree (and C.15 does not arise). |
| 2026-11-18 | **The spec stays the source of a model; an edit made anywhere is a spec change. Not ruled: the owner's leaning, to keep in mind.** A model is a reproducible, verifiable build from a spec, and that is worth keeping when models come to be created and edited in ProjectCommand, which is expected. So a model is never hand-edited and edits do not pile up in the file: a tool that changes a model exports a spec, and the model is rebuilt from it (M.16). Project records (progress, approvals, checks, actual cost) are not design and stay additions carried through a rebuild. The rule about not changing a producer's entities is, since we are the producer, a rule about issued states: nothing issued is changed silently. |

| C.15 | Disputed rules (ruled 2026-11-25, see Decisions). **GRF005**, 32 outputs: every model in metres on a map in feet. The standard is plain: IfcMapConversion transforms the local engineering system into the map's, by "a scaling of the three axes (x,y,z), by the same IfcMapConversion.Scale", then a rotation, then a translation by Eastings and Northings, and Scale "must have the value of the scale from the source to the target units" (IFC4.3 documentation, `IfcMapConversion.md`). So local times Scale is map, and a metre model on a US-foot CRS has Scale 3.28083; IfcOpenShell's conversion agrees and documents 0.001 for a millimetre project on a metre CRS. The rule, read at the commit CI pins (`893f827`, release 1.0.2), quotes the same sentence in its description and its step reads "the quotient of the project length units and the target CRS length units", both giving 3.28083; but its code divides the CRS unit by the project unit (`features/steps/steps/crs.py`), giving 0.3048, and its own passing test file is a metre project on a US-foot CRS with Scale 0.3048. For the millimetre case the rule would want 1000. It is tagged industry practice. A model authored in the map's own units has Scale 1 and does not meet the rule. The owner's call, 2026-11-25: wait for upstream. The report to buildingSMART is drafted and is the owner's to file; when the rule is fixed, GRF005 leaves the baseline and nothing else changes. Until then a metre-authored model on a foot CRS is not accepted into the corpus; the reference job, authored in feet, is. The separate list and the consumer's handling of it are built only if upstream does not act and such a model has to be accepted. | Ruled; waits on upstream. Not scheduled |

## The model as the estimate's record

Goal: an element modelled for one bid arrives in the estimating system as a
thing that can be found, compared and scaled on the next: a D89 headwall of a
stated height on a stated pipe, with the dimensions its concrete comes from
and the sheet it was checked against, where today it arrives as a volume.

What is there today: `est-bim model-elements` sends GlobalId, name, IFC class,
structure id and quantities in the estimate's units (`bimforge/bim/model_elements.py`).
The emitter already writes Length, Width and Height beside volume on some
elements; nothing writes a `Formula`, a class reference or an approval.

## Earthwork

Goal: earthwork as first-class elements: measured, priced and scheduled as
it is built, shown changing the ground in a 4D view, and read the same by
any IFC tool. Ruled 2026-11-25 with the goal order under Decisions. The road
corridor's earthwork (P.6) measures soundly: from the subgrade, so the
pavement is not counted twice, and in exact columns between the design
surface and the ground. What these rows change is what that measurement
becomes. Figures are from the hypothetical road-and-bridge test project's
corridor (9,319 ft, two bridges, 61 cut and 64 fill bands).

Order (set 2026-11-25): the shapes and checks first, then what decides a
balance, then the 4D work, then the agency comparison.

1. E.5 and G.5, with stage 1 (gates clean): the earthwork's shapes and its
   carve check are trusted before its numbers are worked on, and everything
   after is written in its final form.
2. E.3, E.2, then E.4's stripping, before the test road's corridor is called
   final: each changes its balance or its cost. E.2 leans to rock and soil
   as two elements per band, since a schedule takes rock apart. Stripping comes
   first in E.4 because it lowers the ground every volume is measured from;
   then keying and benching, then unsuitable material; structure excavation
   joins the haul when the families that dig it supply it (P.5).
3. E.7, after E.2 and E.3, whose segments and materials it divides by.
4. E.1 when ProjectCommand can apply a cut to the ground in plan; worth most
   after E.7, so a 4D view has the pieces to show.
5. E.6 with W.12 (stage 4), when models are compared with bid quantities.

| ID | Item | State |
|---|---|---|
| E.1 | The existing ground stays whole, and a cut voids it. The corridor already writes each cut voiding the TERRAIN (#364), the standard form, and the one a 4D view needs: a viewer takes a cut out of the ground when its task is done, where a terrain carved at build time shows every pit from the first day. The cost is in the viewer: a full 3D boolean of 61 cuts against the test road's terrain did not finish in 50 min, so that project wrote its cuts unhosted. The ground is a height field, so a viewer can apply its voids in plan, far more cheaply; ProjectCommand is asked to. The finished grade as a surface of its own is G.10, so a viewer that can do neither still shows the end state. The carve stays, as a check (G.5). | Planned |
| E.2 | Rock and soil apart. A cut is one volume with one swell today, and records only how deep the rock lies (`RockDepth`), though the corridor knows the rock surface (`rock.depth_at`). Each cut is split there into soil and rock, each with its own volume, swell and pay code, and the mass haul takes rock's own bulking (bank rock to compacted rockfill). The test road's balance was made outside BIMForge with rock at 4x soil and its own 30 % swell, which the model could not state. | Planned |
| E.3 | The haul ends at a structure. `masshaul.py` runs one cumulative ordinate down the whole line, across bridges, so a balance can rest on hauling across water. A structure gap ends a haul segment; the mass haul reports each segment's balance, and material crossing a structure is a stated choice, not an artefact. | Planned |
| E.4 | The earthwork a model leaves out: clearing and grubbing; topsoil stripped under the cut and fill, and its replacement; fills keyed and benched into hillsides; unsuitable material; and the structure excavation and backfill of the other families (bridges, culverts, walls), which never reach the road's mass haul. Each is a pay item and each moves the balance. | Planned |
| E.5 | Earthwork written as triangle meshes. Each band is written as an IfcFacetedBrep whose coplanar triangles are merged into faces (`bimforge.author.facets`). The ground side follows the terrain's triangles, which are seldom coplanar, so the merge saves little and costs much: on the test road's 64 fills, 50,113 merged faces against 58,494 triangles, but about 180,000 entities and 8.8 MB against about 130 entities and an estimated 2.5 MB as IfcTriangulatedFaceSet (one point list and one index list per element), on a 29.9 MB file. The merge is also where the shapes broke: a cut band written 81 % under its volume, and a fill face of 112 points enclosing 2.69 m2 with two holes, which web-ifc could not triangulate. The volume in the quantity set is computed from the columns, not read off the shape, so it does not change; a closed IfcTriangulatedFaceSet (`Closed` true only when it is) is a solid whose volume the post gate checks as now; Revit and Tekla read it through IFC4; web-ifc loads it fastest. The cost is the look: edge views draw every triangle where merged faces drew clean outlines, so viewers are asked to draw feature edges only. **Backup:** IfcPolygonalFaceSet, the same indexed point list with merged polygonal faces and inner loops, if triangle edges look wrong in practice; it keeps the merge, so the slivers are fixed there first. | Planned |
| E.6 | The agency's method beside ours. Earthwork volumes are exact; an engineer's quantity is usually average end areas between cross sections at 25 or 50 ft. Courses already report both (`average_end_area_cf`); earthwork reports both too, so a difference in W.12 is the design's and not the arithmetic's. | Planned |
| E.7 | Earthwork divided as it is built. Beside the 100 ft takeoff bands, earthwork can be divided as the work is scheduled: cut and fill per haul segment (E.3), fill in lifts (`bimforge.author.lifts`), rock apart (E.2), each an element a 4D task is assigned to (`est-bim schedule`). | Planned |

## Geometry: checks and outputs

From a review on 2026-11-14 of how bodies are created and checked, against
how open-source CAD kernels work. The ten shipped examples were rebuilt and
measured: every body is a closed solid, 139 of 158 are exact parametric
solids (extrusions and revolutions), and each matches its stated volume
within the gate's 0.5% tolerance. These rows are not yet listed in the
platform roadmap's Phase 4.

| ID | Item | State |
|---|---|---|
| G.1 | The QTO and bar-schedule workbooks are not byte-identical between rebuilds. `openpyxl` overwrites the modified time on save, so pinning it in `emit_qto.py` and `emit_bbs.py` has no effect; the created time is pinned correctly. `takeoff_workbook._save_deterministic` rewrites the modified time after saving: reuse it, and test it. | Next (bug) |
| G.2 | An overlap gate. No check finds two elements occupying the same space, which is how a headwall's double-counted concrete passed (10.134 against 9.967 cy, #24). Bounding boxes first, then the common volume, with an opt-out for catalog examples that place alternatives together. | Next |
| G.3 | Two outputs disagree with the IFC. STEP writes a post as a true cylinder where the IFC writes the equal-area polygon: +0.64% on the posts alone and about +0.25% on their element, inside the 0.5% tolerance today and outside it at fewer segments. The DXF plan of a tube is drawn at the origin, ignoring its position and axis. | Next |
| G.4 | Orientation checked face by face. Edges are compared undirected and volumes taken absolute, so one flipped face lowers the stated and the emitted volume together. A directed-edge check in `mesh_topology`. | Next |
| G.5 | What a terrain carve that cannot run does. The carve (`bimforge.terrain.solid.carve`) closes the ground into a solid and subtracts each excavation with a mesh boolean; it gives up when the optional mesh libraries (`trimesh`, `manifold3d`) are missing or the boolean raises (a ground with holes, a bad excavation solid), and the build goes on with the open surface and `Carved: false`. That hides four things: `Carved: false` reads the same whether no cut was asked for, the libraries were missing or the boolean failed; the same spec builds different files where the libraries are and are not installed; everything that reads the ground (M.13, G.2, G.10) sees the pits full; and which cuts are into existing ground is not known. It also checks nothing when it succeeds: the volume removed is computed and thrown away, and success is not tested for a closed result. A boolean that never returns (61 cuts against a test road's 3DEP mesh ran past 50 min) has no fallback at all. Considered and not taken up:

- One OpenCascade solid as the source of every output. A B-rep cannot
  give back the parametric solids the IFC states, and Revit and Tekla
  import a circle-profile extrusion as a native pipe or rod only because
  the file says it is a circle. It would also replace "quantities from the
  emitted faces".
- `WarpedStem` stating its analytic volume, 0.3% off the facets it emits.
  That is the documented rule for warped and curved primitives: the closed
  form is the pay quantity, and the faceted volume is held to it within
  tolerance.
- Stable names for faces. Faces are classified by direction on every read
  and no face identity is stored anywhere, so there is nothing to keep
  stable.
- Exact-arithmetic or all-manifold booleans. The degenerate-geometry bugs
  on record came from export precision and from readers' kernels, and each
  was fixed more cheaply.
- A cache of built geometry. A build takes 2 to 5 s and the geometry under
  10 ms of it.
